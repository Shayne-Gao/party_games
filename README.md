# Party Games

一个面向线下聚会场景的纯前端小游戏工具箱。

这个仓库不是一个传统意义上的“单页应用”或“前后端分离项目”，而是一个由多个独立 HTML 页面组成的静态站点。每个页面对应一个具体的聚会游戏或主持辅助工具，强调以下特性：

- 打开即用，无需构建
- 手机优先，适合聚会现场直接发给朋友使用
- 绝大多数页面为单文件实现，便于快速修改和分发
- 尽量不依赖后端，能静态部署就静态部署

这份 README 主要用于持久化记录我当前对仓库的理解，方便后续继续迭代时快速对齐上下文。

## 1. 项目定位

从现有代码看，这个项目的核心目标是：

- 给聚会、桌游、朋友局提供一套“开箱即用”的主持辅助工具
- 降低游戏组织门槛，避免主持人临时找纸笔、做卡片、口头分配身份
- 让多个游戏以相同的访问方式存在于一个入口页中
- 在“够用”和“开发速度”之间取平衡，优先快速交付可玩的版本

它更像一个“聚会游戏工具集合站”，而不是一个统一框架下的严格工程化产品。

## 2. 当前项目结构

仓库当前非常轻量，全部逻辑直接写在页面中：

```text
party_games/
├── index.html             # 首页/游戏入口
├── codenames.html         # 行动代号，支持 PeerJS 联机
├── guess_word.html        # 你比划我猜 / 猜词达人
├── whoisspy.html          # 谁是卧底
├── zhuogui.html           # 捉鬼游戏
├── role_dispenser.html    # 通用自定义发牌器
└── README.md              # 项目理解与说明
```

## 3. 技术实现特征

### 3.1 总体实现方式

整个仓库目前采用最直接的实现路线：

- HTML + CSS + 原生 JavaScript
- 每个页面独立维护自己的状态和交互
- 没有打包器、构建脚本、模块系统、测试体系
- 没有统一样式库，也没有公共组件抽象

这意味着：

- 优点是改起来快、部署简单、迁移成本低
- 缺点是页面之间会有重复逻辑，长期维护时容易出现风格和行为分叉

### 3.2 运行方式

这是一个纯静态项目，通常只需要一个静态文件服务器即可运行。

本地预览示例：

```bash
cd party_games
python3 -m http.server 18080
```

然后访问：

```text
http://127.0.0.1:18080/
```

### 3.3 依赖情况

大多数页面没有外部依赖。

唯一明确使用外部脚本的是：

- `codenames.html`
  - 通过 CDN 引入 `PeerJS`
  - 用于房主/玩家之间的点对点同步

这也意味着，`codenames.html` 在离线环境下不一定能完整工作。

## 4. 首页理解

`index.html` 的职责很清晰：它不是业务页，而是工具导航页。

当前首页特点：

- 使用内嵌 `games` 配置数组驱动列表渲染
- 卡片风格偏移动端、暗色、轻赛博感
- 所有入口都是跳转到同目录下的独立 HTML 页面
- 页面没有复杂状态，属于纯展示和导航层

这说明首页后续比较适合继续承担：

- 游戏入口管理
- 游戏状态标识（例如“推荐”“联机版”“开发中”）
- 玩法简介
- 版本说明或最近更新

## 5. 各页面功能理解

### 5.1 `codenames.html`

这是仓库里相对最“产品化”的页面之一，核心是一个简化但可联机的《行动代号》工具。

玩法定位：

- 适合分成两队进行联想词对抗
- 更适合有一个“发起人/房主”先建房，再让其他人加入
- 页面主要承担的是“共享牌面”和“同步翻牌”，不是完整裁判系统

推荐使用方式：

- 1 人作为房主创房
- 其他玩家输入相同房间号加入
- 每队至少有队长和队员
- 所有人围绕同一块牌面讨论和翻牌

一局的基本流程：

- 房主输入房间号，必要时录入自定义词库
- 玩家选择自己身份后加入
- 房主建房后生成 25 张词牌和颜色分布
- 队长根据颜色给提示，队员根据提示点选词牌
- 点击某张牌后先进入待确认状态，再次点击才正式翻开
- 牌面翻开后，所有连接中的设备同步更新

当前能力：

- 支持房主创建房间
- 支持其他玩家加入同一房间
- 支持选择身份：队员 / 队长
- 支持房主输入自定义词库
- 自动生成 25 张词牌和颜色分布
- 队长可以直接看到颜色归属
- 翻牌需要二次确认，减少误触
- 通过 PeerJS 同步翻牌、日志和重开操作

我对它的实现理解：

- “房间号”既用于 PeerJS 的房主 ID，也用于生成固定随机种子
- 因此同一个房间号可以稳定生成同一套词与颜色分布
- 房主生成游戏数据，加入者通过连接后的 `sync` 消息拿到完整状态
- 页面没有完整的回合同步系统，更像一个“联网共享牌面工具”

页面里的内容设计：

- 默认内置了一大批中文词语，覆盖地点、职业、动物、物品、抽象概念等
- 支持手动输入自定义词库，分隔方式兼容空格、逗号和换行
- 红蓝双方人数分布会根据先手自动变成 9:8 或 8:9
- 页面内还有简单日志区，用来记录翻开的词和时间

适合补充进 README 的玩法提醒：

- 当前页面没有强约束“哪一队回合中”
- 也没有内置“提示词合法性”校验
- 因此它更适合作为半主持式工具，而不是完全自动执法的游戏系统

适合后续增强的方向：

- 增加断线重连/重新同步
- 区分主持端和玩家端权限
- 增加胜负判定和回合控制
- 增加词库管理

### 5.2 `guess_word.html`

这是一个非常典型的“你比划我猜 / 你演我猜”单机页面，明显以手机现场使用为核心。

玩法定位：

- 适合两队轮流挑战，或者一个人拿手机、其余人负责表演/提示
- 重点不是复杂规则，而是高节奏、强反馈和一局结束后的复盘
- 这是一个典型的“把手机扣在额头上”的玩法页

推荐使用方式：

- 开局前先选分类和时间
- 手机举在额头前，屏幕朝向队友
- 队友通过描述、表演、联想帮助持机人猜词
- 猜对就扣下手机或点击左侧
- 跳过就仰头或点击右侧

一局的基本流程：

- 进入页面后选择词库分类和计时长度
- 点开始后请求重力感应权限，并进入倒计时
- 页面开始连续出词
- 每次正确或跳过都会立即切到下一个词
- 时间结束后显示最终得分、正确数、跳过数和完整历史记录

当前能力：

- 选择词库分类
- 选择倒计时时长
- 倒计时开始前有简单读秒
- 支持重力感应操作
- 同时也支持左右点击触发，作为兼容方案
- 正确/跳过会有闪屏、蜂鸣、震动反馈
- 结束后展示得分与完整复盘记录

我对它的实现理解：

- 词库直接写在页面内的纯文本块中
- 页面启动后会解析为类别和词表
- 游戏主循环非常直接：出词 -> 用户动作 -> 记录结果 -> 下一词
- 结束时会把当前还没猜出的词补到历史中，方便复盘

页面里的内容设计：

- 词库分了多个主题，例如经典影视、动物世界、成语名句、网络热梗、地理常识、生活用品、童年回忆、美食大赏
- 每个主题都偏中文语境、朋友局熟悉度高、适合快速描述
- 页面重点做了即时反馈，包括颜色闪屏、声音提示、震动和顶部时间条
- 结束页不是只显示分数，而是把每个词的结果都列出来，便于赛后复盘和争议确认

适合补充进 README 的玩法提醒：

- 重力感应在不同手机上灵敏度可能不同
- 页面已经提供了点击左右半屏的兼容交互
- 如果是多人轮流比拼，这个页面天然适合做“每队一轮”的计分工具

这个页面的特点是“单机体验完成度高”，并且已经开始考虑：

- iPhone 权限申请
- 全屏体验
- 降级交互
- 游戏结束复盘

### 5.3 `whoisspy.html`

这是“谁是卧底”的经典发牌 + 投票辅助页。

玩法定位：

- 适合熟人局、聚会局、饭桌局
- 规则非常直观，主持人只需要负责配置人数和发牌
- 页面设计目标就是把传统纸条发身份的流程数字化

推荐使用方式：

- 主持人先配置总人数、卧底人数和是否带白板
- 所有人输入昵称后，轮流查看自己的词语
- 发牌结束后开始描述、讨论和投票
- 每轮被投出的人在页面中标记出局

一局的基本流程：

- 选择词库主题
- 配置总人数、卧底人数、白板人数
- 为每位玩家填写昵称
- 点击发牌后，手机在玩家之间轮流传递查看身份
- 全员看完后进入投票页
- 每轮投票后手动标记出局玩家，页面根据存活阵营判断胜负

当前能力：

- 配置总人数、卧底人数、白板人数
- 选择词库主题
- 输入玩家昵称
- 单手机轮流翻牌查看身份
- 发牌后进入投票页
- 可以点击标记某玩家出局
- 可以查看或隐藏当前阵营存活统计
- 自动给出平民胜利 / 卧底胜利判断

我对它的实现理解：

- 玩法聚焦在线下同屏传手机，而不是联机分发
- 词库结构是“平民词 | 卧底词”的成对数据
- 白板用固定 `???` 表示
- 游戏阶段分成配置页、发牌页、投票页三段式流程

页面里的内容设计：

- 预置了多个常见主题，如日常生活、美食佳肴、数码科技、影视娱乐、童年回忆、职场风云、运动竞技、大好河山、动物世界、文学经典、自然科学
- 每个主题都是“相似但不完全相同”的双词结构，适合谁是卧底的核心博弈
- 页面会同步显示平民、卧底、白板的配置结果，方便主持人检查人数是否合理
- 投票页除了标记出局外，还内置了一个可折叠的存活统计栏，减少主持人口算负担

适合补充进 README 的玩法提醒：

- 当前的投票过程需要线下自行讨论，页面不代替真实发言环节
- 页面负责的是发身份、记录出局和显示当前阵营状态
- 白板玩法已经内置，但白板是否可以“猜词翻盘”等扩展规则，仍然需要玩家自行约定

这个页面的优点是结构清晰，逻辑闭环完整，适合继续增强成更成熟的主持工具。

### 5.4 `zhuogui.html`

这是一个更偏“变体玩法”的阵营发牌工具，支持 A/B 两组好人、鬼阵营，以及可选白板。

玩法定位：

- 这是一个“异词阵营推理”玩法，不是标准谁是卧底
- 两组好人分别拿到相近但不同的词，鬼阵营只拿提示
- 玩家既要判断谁像鬼，也要防止把另一组好人误当成敌人

推荐使用方式：

- 适合 6 人以上、愿意接受一点变体规则的聚会局
- 主持人只需要设总人数和是否加入白板
- 页面会自动计算 A 组、B 组和鬼的数量
- 发牌后开始自由发言、试探、投票

一局的基本流程：

- 选择词库分类
- 设置总人数，并决定是否加入白板
- 所有人填写昵称
- 系统自动分配 A 组、B 组、鬼和可选白板
- 玩家依次看牌
- 看牌结束后进入投票页，主持人根据实际投票结果在页面中标记出局
- 页面根据存活结构实时判断胜负

当前能力：

- 根据总人数自动分配 A 组、B 组、鬼人数
- 可选是否加入白板
- 选择词库分类
- 玩家轮流看身份
- 鬼看到的是提示信息，不是与好人相同的词
- 进入投票页后可标记出局
- 会根据局面实时判断胜负

我对它的实现理解：

- 这个页面不是传统“谁是卧底”，更像一个“捉鬼”或“异词阵营推理”变体
- 数据源中每条词库不仅有 A 词、B 词，还有给鬼看的提示信息
- 胜负条件包含：
  - 鬼全部出局则好人赢
  - 鬼人数大于等于好人总数则鬼赢
  - A 组或 B 组任意一组灭绝则鬼赢

页面里的内容设计：

- 每条词库数据都包含三层信息：A 词、B 词、鬼的提示
- 提示信息里还会带字数辅助，方便鬼阵营有基本方向但不至于直接知道答案
- 词库主题覆盖食物、数码、日常、职场、童年、运动、地理、娱乐、动物、文学、科学、影视等
- UI 上会直接展示本局阵营配比，让主持人快速确认当前规则结构

适合补充进 README 的玩法提醒：

- 这是一个更依赖线下口头规则约定的变体游戏
- 白板属于好人阵营，但具体是否拥有额外能力，需要局前说明
- 页面已经内置胜负判断，但“发言轮次”“鬼能否自爆”“白板翻盘”等扩展规则不在系统里

这说明作者已经不只是做“发牌器”，而是在实现带规则约束的主持辅助工具。

### 5.5 `role_dispenser.html`

这是一个通用化程度最高的页面，已经不是某个固定游戏，而是可自定义的发牌基础设施。

玩法定位：

- 它不是单一游戏，而是一个“把任何身份分配类玩法快速落地”的模板工具
- 适合桌游主持人、剧本杀私设玩法、临时分组活动、派对惩罚任务、阵营分配等场景
- 如果现成的几个游戏都不完全符合需求，这个页面就是兜底方案

推荐使用方式：

- 先把本局需要的身份组逐个建出来
- 为每个组填写人数和该组看到的内容
- 输入玩家昵称
- 让所有玩家轮流查看自己的卡牌
- 进入投票/淘汰页后，用页面辅助记录谁已出局以及各组剩余人数

一局的基本流程：

- 在配置页添加或删除身份组
- 为每个组设置组名、人数、词语或身份说明
- 输入玩家昵称
- 点击开始后，系统按配置生成身份池并随机发放
- 玩家逐个看牌
- 发牌完成后进入游戏进行页
- 通过投票板记录出局情况，并查看各组剩余人数


当前能力：

- 自定义多个身份组
- 每个组可设置组名、人数、词语/内容
- 自动计算总人数
- 自动生成对应数量的玩家输入框
- 支持保存组配置和玩家昵称到 `localStorage`
- 支持清空缓存
- 发牌完成后可进入投票和存活统计界面

我对它的实现理解：

- 这个页面可以作为很多桌游/派对玩法的通用底座
- 当前保存的是“配置数据”，不是完整的对局过程
- 游戏过程仍然是“单机传手机看身份”
- 投票页支持按组统计剩余人数

页面里的内容设计：

- 每个组有三项核心信息：组名、人数、看到的内容
- 页面会自动根据总人数生成玩家昵称输入区
- 组配置和昵称会持久化保存到 `localStorage`
- 存活统计是按组汇总的，而不是固定按“平民/卧底”这样的预设阵营写死

适合补充进 README 的玩法提醒：

- 这是一个通用工具，不自带固定胜负规则
- 页面负责发放信息和记录淘汰，不负责定义玩法本身
- 最适合那些“规则由主持人自己定，但又不想手写纸条”的场景

它是当前仓库里最值得继续抽象和扩展的页面之一，因为它天然适合作为“模板能力”沉淀。

## 6. 产品层面的整体理解

如果把这几个页面放在一起看，我认为这个仓库已经呈现出比较明确的产品方向：

- 不是做单个爆款小游戏
- 而是在做“聚会桌游主持人工具箱”

这些页面背后有几个统一设计思路：

- 都尽量适配手机
- 都强调现场快速开局
- 都尽量减少外部依赖
- 都允许一个设备在多人之间传递查看
- 都把主持成本前置为简单的配置动作

换句话说，这个项目的“共同内核”不是视觉风格，而是：

- 线下社交场景
- 快速开局
- 低学习成本
- 主持辅助

## 7. 数据与状态管理现状

当前仓库的数据管理非常分散，但也很好理解：

- `index.html`
  - 静态配置数组
- `guess_word.html`
  - 页面内嵌词库文本
  - 运行时内存状态
- `whoisspy.html`
  - 页面内嵌词库对象
  - 单局状态全在内存中
- `zhuogui.html`
  - 页面内嵌词库对象
  - 单局状态全在内存中
- `role_dispenser.html`
  - 配置数据写入 `localStorage`
  - 对局过程状态在内存中
- `codenames.html`
  - 本地运行时状态 + PeerJS 同步

这意味着后续如果要提升维护性，可以考虑两个方向：

- 继续保持“每页自包含”，但提炼统一数据格式
- 或者逐步抽出公共脚本/样式，提高复用率

## 8. 已知细节与注意点

基于当前代码，我先记录几个已经观察到的点，后续迭代时值得优先关注：

- `index.html``games` 配置里“自定义发牌工具”的文件名写成了 `" role_dispenser.html"`，前面多了一个空格。
  - 当前浏览器环境下入口仍可打开，但这是一个不够规范的细节，后续仍建议修正。
- `codenames.html` 的联机依赖 `PeerJS` CDN。
  - 如果网络环境受限，页面可能无法正常建房或加入。
- 多个页面把词库和逻辑全部写在单文件里。
  - 早期开发很快，但词库继续增大后，可读性会迅速下降。
- 页面之间存在重复的“发牌/翻牌/投票/状态统计”模式。
  - 说明后续有空间抽公共能力。
- 大量逻辑依赖浏览器原生能力。
  - 例如重力感应、震动、音频上下文、全屏、`localStorage` 等，不同手机兼容性会有差异。
